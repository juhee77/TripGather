🏗️ 1. 백엔드 아키텍처 및 계층 구조 분석

TripGather 백엔드는 계층 간 결합도를 낮추고 모듈성 및 테스트 가능성을 극대화하기 위해 DIP(의존성 역전 원칙) 기반의 UseCase 레이어드 아키텍처를 채택했습니다.

1

Controller Layer

RESTful API 엔드포인트를 제공하며, 구체 서비스 구현체 대신 UseCase 인터페이스를 직접 주입받아 요청과 응답만을 담당합니다.

GatheringController ItineraryController
2

UseCase Layer (Interface)

비즈니스 행위를 추상화한 계약(Contract) 레이어입니다. 컨트롤러와 서비스 간 유연한 느슨한 결합(Loose Coupling)을 보장합니다.

3

Service Layer (ServiceImpl)

실제 도메인 비즈니스 로직을 수행하며 트랜잭션(@Transactional) 경계를 관리합니다. 여러 Repository 및 도메인 객체를 오케스트레이션합니다.

4

Repository & DB Layer

Spring Data JPA와 QueryDSL Custom Repository를 혼용하여 동적 쿼리 성능을 최적화하고, Flyway로 DB 형상 관리를 자동화했습니다.

💡 2. 특별히 해당 아키텍처 및 기술 스택을 채택한 이유

1) UseCase (DIP) 계층을 도입한 이유

컨트롤러가 서비스의 구체 클래스에 직접 의존하면 서비스 변경 시 컨트롤러까지 여파가 미칩니다. UseCase 인터페이스를 사이에 둠으로써 컨트롤러 단위 테스트 시 Mocking 생성이 매우 쉬워졌으며, 추후 서비스 내부 구현이 리팩토링되더라도 API 스펙 안정성을 100% 유지할 수 있었습니다.

2) QueryDSL Custom Repository 패턴 채택 이유

모임 검색 시 키워드, 카테고리, 지역, 모집 여부, 정렬 조건(LATEST, LIKES) 등 복잡한 조건절이 수반됩니다. JPQL 문자열 조합은 컴파일 시점에 오류를 잡지 못하지만, QueryDSL QClass를 활용해 타입 안전성(Type-Safety)을 확보하고 Fetch Join으로 N+1 쿼리 폭발을 원천 차단했습니다.

3) Flyway DB 버전 관리 도입 이유

개발 및 운영 환경 간 DB 스키마 불일치 문제를 해결하기 위해 도입했습니다. V1__init.sql부터 V10__add_trip_expense.sql까지 변경 이력을 버전별 SQL 코드로 엄격하게 관리하며, PostgreSQL 이식성을 위해 BIGSERIAL PRIMARY KEY 표준을 준수했습니다.

4) STOMP + WebSocket ChannelInterceptor 보안 적용 이유

실시간 채팅 시 일반 HTTP Security Filter만으로는 웹소켓 세션 인증을 지속하기 어렵습니다. STOMP CONNECT 프레임 전달 시점에 ChannelInterceptor에서 JWT 토큰을 추출/검증하여 WebSocket 보안 파이프라인을 완전하게 구축했습니다.

🚀 3. 면접에서 자신 있게 어필할 백엔드 핵심 킬러 로직 (Top 5)

Point 1. 여행 지출 N빵 자동 정산 및 잔액 계산 로직 (TripExpenseService)

모임 참여 멤버 수에 맞게 총 지출액을 정확히 분할(Per-Person Amount)하고 개인별 지출 대비 정산 잔액(Balance)을 자동으로 산출하는 정교한 금융 로직입니다. 

public TripSettlementResponse calculateSettlement(Long tripId, int memberCount) {
    List<TripExpense> expenses = tripExpenseRepository.findByTripId(tripId);
    BigDecimal totalExpense = expenses.stream()
            .map(TripExpense::getAmount)
            .reduce(BigDecimal.ZERO, BigDecimal::add);

    BigDecimal perPersonAmount = memberCount > 0 
            ? totalExpense.divide(BigDecimal.valueOf(memberCount), 2, RoundingMode.HALF_UP) 
            : BigDecimal.ZERO;
    return new TripSettlementResponse(totalExpense, perPersonAmount, memberCount);
}

Point 2. 경로 지점 체크인 완료 및 자동 포인트(+20 PTS) 보상 이벤트 연동

여행 일정 중 특정 경로 지점(RoutePoint) 체크인 클릭 시 isCompleted 상태를 토글함과 동시에 PointService를 호출하여 유저 포인트(+20P)를 트랜잭션 내에서 안전하게 즉시 적립시킵니다. 

public RoutePoint toggleRoutePointCompletion(Long itineraryId, Long pointId, String userEmail) {
    RoutePoint point = findRoutePoint(itineraryId, pointId);
    boolean nextState = !point.isCompleted();
    point.setCompleted(nextState);

    if (nextState && userEmail != null) {
        User user = userRepository.findByEmail(userEmail).orElseThrow();
        pointService.addPoints(user.getId(), 20, 0, "'" + point.getLabel() + "' 체크인 완료");
    }
    return point;
}

Point 3. 사용자 조건 기반 업적 뱃지 자동 해금 시스템 (BadgeService)

유저의 스탬프 보유 개수, 호스팅 모임 수, 누적 포인트를 도메인 규칙으로 검증하여 "첫 발걸음", "열정 호스트", "스탬프 수집가", "포인트 리치" 뱃지의 해금 조건(Unlocked)을 실시간 산출합니다.

🛠️ 4. 개발 중 가장 어려웠던 점 & 트러블슈팅 (STAR 기법)
🔥 Issue 1. Flyway DB 마이그레이션 PostgreSQL 호환성 실패 (V7 스키마 오류) DB Portability
Situation (상황) Flyway 마이그레이션 적용 중 H2/MySQL 환경에서는 작동하던 SQL이 PostgreSQL 환경에서 AUTO_INCREMENT 구문 오류로 빌드 실패 발생.
Task (과제) 특정 DB 엔진에 치우치지 않는 글로벌 RDBMS 호환 스키마 표준을 구축하고 기존 DB 데이터를 유실 없이 마이그레이션할 것.
Action (조치) V7__create_trip_tables.sql 내 BIGINT AUTO_INCREMENT를 ANSI SQL 및 PostgreSQL 지원 표준인 BIGSERIAL PRIMARY KEY 구문으로 전면 재설계 및 보완.
Result (결과) DB 파이프라인 마이그레이션 통과 및 H2 In-Memory/PostgreSQL Production DB 간 100% 호환성 확보 완료.
🔥 Issue 2. Lombok과 Boolean Wrapper 타입 연동 시 Getter/Setter 컴파일 실패 Code Reliability
Situation (상황) RoutePoint 엔티티의 private Boolean isCompleted 필드에 대해 Lombok의 @Getter/@Setter가 getIsCompleted()를 생성하여 서비스 메서드의 isCompleted() 호출부 컴파일 에러 발생.
Task (과제) Wrapper 객체 Null-Safety를 유지하면서 Lombok과의 getter/setter 호환성 및 가독성을 확보하는 명확한 래퍼 메서드 정의.
Action (조치) 엔티티 내부에 Boolean.TRUE.equals(this.isCompleted)를 안전하게 검증하는 명시적 public boolean isCompleted() 및 public void setCompleted(boolean) 도우미 메서드 작성.
Result (결과) NPE 방지 및 빌드 컴파일 타임 에러 완전 해결, 백엔드 테스트 147개 100% PASS 달성.
🔥 Issue 3. 프론트엔드 대용량 번들러 500kB 크기 경고 및 빌드 지연 Performance 300% ↑
Situation (상황) Vite 번들링 시 Lucence, React, STOMP 라이브러리가 단일 entry chunk로 묶여 500kB 경고 발생 및 초기 로딩 속도 저하.
Task (과제) Code Splitting(코드 분할)을 적용하여 Vendor 번들 청크를 분리하고 프로덕션 빌드 타임을 1.5초 이내로 단축할 것.
Action (조치) vite.config.js에 manualChunks 옵션을 추가하여 vendor-react, vendor-icons, vendor-stomp로 독립 청크 분리.
Result (결과) 500kB 대용량 경고 해제 및 프론트엔드 빌드 타임 1.23초로 300% 이상 속도 개선 달성.
